# DeskPartner 产品工作模型与 Headless 优先决策

> 日期：2026-10-19  
> 状态：已形成方向，作为后续设计与实施的上位约束  
> 关联：`docs/prd/DeskPartner-PRD.md`、`docs/architecture/agent-usage-contract.md`、`docs/design/2026-10-18-full-product-experience-scenarios.md`

## 1. 本次决策

DeskPartner 后续不再以“看板产品”作为默认产品模型，而定义为：

> **DeskPartner 是本地优先的人机共享工作空间。它让人和 Agent 在同一份工作上下文中完成理解、提议、执行、沟通、验收和交接。事项是具有责任、下一步和完成判据的正式工作承诺；看板是人查看和裁决这些承诺的项目内视图。**

实施顺序采用 **Headless 优先、GUI 后置重做**：

```text
产品工作模型
→ Headless Agent 契约
→ Headless 垂直闭环
→ 独立 Agent 实测
→ 修正契约与领域边界
→ GUI 原型
→ GUI 实现
→ 人类视觉验收
```

这不是重写全部产品，也不是另起一套独立系统。保留现有数据库、迁移、仓储、权限、CLI、MCP 和验证基础，在其上重构 Agent 的高层工作入口；GUI 后续作为已验证能力的人类控制面和可视化界面。

## 2. 为什么不再看板驱动

看板最初由“聊天中的承诺容易丢失”逐步演化出来：事项 → 状态 → 状态列 → 项目和协作能力继续挂到看板旁边。这个过程解决了可追踪性问题，却把一个有效视图误当成了总体工作模型。

看板适合回答：

- 哪些正式工作承诺正在推进；
- 谁负责；
- 哪些事项等待人、等待 Agent 或等待验收；
- 哪些事项阻塞；
- 项目进度如何。

看板不负责：

- 介绍 DeskPartner 是什么；
- 让 Agent 认识用户和协作边界；
- 保存项目全部背景和历史决定；
- 承载所有通知、日志和对话；
- 替代审批、对话或项目资料；
- 作为 Agent 的默认首入口。

因此：

```text
项目 ≠ 看板
事项 ≠ 所有工作信息
看板 ≠ 数据模型
Agent ≠ 看板的另一个拖拽操作者
```

## 3. 核心对象与载体边界

| 对象 | 负责什么 | 不负责什么 |
|---|---|---|
| 用户上下文 | 用户是谁、怎样工作、希望 Agent 如何协作 | 不替代项目背景 |
| 协作方式 | 可以直接做、需要询问或需要审批的边界 | 不等于一次审批记录 |
| 项目 | 持续工作的目标、背景、资料和决定 | 不等于某个看板 |
| 决定 | 为什么采用某个方向、当前是否仍有效 | 不等于执行日志 |
| 工作承诺（事项） | 有责任人、下一步和完成判据的正式工作单元 | 不承载所有闲聊和想法 |
| 对话/评论 | 讨论、提问、补充、驳回理由和交接 | 不替代正式决定和事项状态 |
| 审批 | 主用户对接入、高风险动作和内容提议做裁决 | 不由 Agent 自己批准 |
| 执行证据 | 谁做了什么、结果、失败和时间 | 不替代用户验收 |
| 视图 | 工作台、看板、列表、时间线等呈现方式 | 不改变底层事实 |

一个内容只有在需要采取行动、需要判断完成与否、且需要跨会话持续追踪时，才适合进入事项；否则优先放在对话、决定、资料、通知或活动记录中。

## 4. 三个核心循环

### 4.1 理解循环

```text
认识用户 → 理解协作方式 → 理解项目背景 → 找回历史决定
```

### 4.2 推进循环

```text
形成承诺 → 执行或提议 → 等待审批/补充信息 → 交付结果 → 人验收或驳回
```

### 4.3 交接循环

```text
记录当前状态 → 记录已经做过的决定 → 记录剩余工作和阻塞 → 更换 Agent 或中断后继续
```

看板主要服务推进循环和交接循环中的状态观察；不是理解循环的中心。

## 5. 两类核心用户的首入口

### 5.1 人类用户

人首先需要知道：

```text
我现在需要处理什么？
哪个 Agent 在等我？
哪些结果需要我验收？
哪个项目需要关注？
```

因此未来 GUI 的默认首页应是面向行动的工作台，而不是完整全局看板。

### 5.2 Agent

Agent 首先需要知道：

```text
我正在服务谁？
用户希望怎样协作？
当前项目目标是什么？
最近发生了什么决定？
当前有哪些可继续工作？
我应该执行、提议、询问还是等待？
```

Agent 的首入口应是上下文和下一步，而不是完整事项列表。

## 6. Headless 优先的范围

### 6.1 Headless 必须先验证的闭环

```text
接入
→ 认识用户
→ 理解协作方式
→ 进入项目
→ 找到历史决定
→ 找到当前可继续工作
→ 执行或提交提议
→ 等待审批
→ 回读结果
→ 留下交接记录
```

### 6.2 建议的高层能力

命名暂不固化，但能力边界必须先固化：

- 获取当前工作上下文（context）；
- 获取项目上下文（project context）；
- 获取推荐的下一步工作（work next）；
- 有界搜索决定和证据；
- 提交动作或提议；
- 查询审批和执行结果；
- 写入交接记录。

高层入口通过现有 CLI/MCP、仓储和权限层实现，不另造第二套数据库或门禁。

### 6.3 统一返回要求

每个读取结果应说明：

- 当前结果是什么；
- 匹配、返回和截断数量；
- 是否有下一页或更深层入口；
- Agent 下一步可以调什么。

每个写入结果应说明：

- 直接写入、提议还是审批申请；
- 是否需要主用户处理；
- 审批后是否立即执行；
- 以谁的身份落账；
- 如何查询最终结果；
- 失败后如何继续。

### 6.4 人的最小控制面

Headless 阶段不代表取消人的控制。至少必须有可靠的人类入口处理：

- 批准或拒绝 Agent 接入；
- 采纳或拒绝档案、协议、接手说明提议；
- 批准高风险操作；
- 验收或驳回交付；
- 查看失败原因；
- 撤销权限。

Agent 不得批准自己，也不得通过修改权限矩阵绕过控制。

## 7. 保留与重做边界

### 保留并复用

- SQLite 数据库与迁移；
- 仓储与领域数据；
- 身份、凭据、审批和权限基础；
- 事项状态、评论、审计与备份；
- CLI/MCP 的兼容入口；
- 测试、构建、打包和隔离验证基础设施。

### 优先重构

- Agent 高层工作入口；
- CLI/MCP 返回与错误契约；
- 上下文、决定、等待关系和下一步的组织方式；
- 提议与审批结果的回读路径；
- GUI 一级信息架构和产品外壳。

### 暂不作为第一阶段目标

- 全部数据库重写；
- 全部旧命令改名；
- 复杂统计和动画；
- 先做完整 GUI 视觉重构；
- 删除看板或事项状态机。

## 8. 对现有 PRD 的影响

现有 PRD v1.5 仍保留大量有效领域需求，但它把“看板/事项”放在了过高的默认位置，也没有明确 Headless 优先的实施顺序。后续需要在 PRD 或新的上位文档中补充：

1. 产品工作模型：为什么不是看板驱动；
2. 对象、载体与视图的职责边界；
3. Agent 的上下文首入口和继续工作契约；
4. Headless 垂直闭环作为 GUI 重做前置；
5. 新的里程碑判据：真实 Agent 体验通过后才进入 GUI；
6. 旧版本计划暂停，待新基线确认后重新拆分。

## 9. 当前明确不做的判断

以下结论尚未被本文件宣称为已实现：

- 当前 CLI/MCP 已经具备完整 Headless 闭环；
- 当前 GUI 已经符合新工作模型；
- 当前 M5 接手实验已经通过；
- 当前所有权限配置都已经改变真实行为；
- 当前事项账实已经完成审计。

本文件是方向和实施约束，不是完成报告。
