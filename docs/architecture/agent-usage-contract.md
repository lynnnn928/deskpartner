# Agent 使用契约与黄金路径

> 状态：设计基准（2026-10-16）
>
> 这份文档定义 DeskPartner 面向 AI 助手的统一使用体验。它不是第二份 CLI 帮助，也不替代 `schema`、`help` 或代码硬关口；命令名、参数、错误码和闸门以运行时出口与 `schema.gates` 为准。

## 1. 产品承诺

DeskPartner 的目标不是让助手记住全部历史，而是让工作在助手更换、会话中断或多人协作后仍可继续：

- 能找到主用户认可的工作方式和协作协议；
- 能在有限阅读成本内了解项目当前情况；
- 能追溯历史决定、事项和证据，而不把历史提议误当成当前事实；
- 能清楚知道一次写入是立即生效、等待审批，还是被拒绝；
- 不能因为 CLI、MCP、GUI 或 Skill 的差异而走出互相矛盾的流程。

## 2. 黄金路径

默认接入顺序如下。除非任务明确要求，否则不要一开始读取全量事项、评论或事件：

```text
Skill L0
  → profile get                       认识主用户
  → protocol get                      读取协作约定与硬关口
  → project get（摘要）                了解项目目标与接手入口
  → project search（有界命中）           找历史决定、依据和相关事项
  → todo list（有界、按状态）            找当前可继续的工作
  → todo get / comment / history        深入一条具体记录
  → 选择下一步并核对验收条件
  → 直接写入或提交 proposal             明确写入语义
  → 查询审批/执行结果                   确认最终状态
```

读取到的材料彼此冲突时，按以下优先级核对：当前数据库事实与用户明确决定 > 当前版本代码和测试证据 > 项目接手说明 > 交付记录与历史文档 > agent 的推断。不能仅凭标题、`fixedInVersion`、子事项完成或旧评论改变状态判断。

## 3. 四个出口必须同源

每项面向 Agent 的能力都必须能回答以下四个问题：

| 出口 | 必须保证 |
|---|---|
| CLI | 命令、参数、退出码、身份和错误码可实际执行 |
| MCP | 工具名、参数、annotations、身份转发和 CLI 语义一致 |
| GUI | 用户能查看必要结果、执行需要人工确认的动作，并看到失败原因 |
| Skill / Guide | 只教真实存在的入口，说明下一步，不复制易漂移的参数表 |

出现出口差异时，先修共享命令定义或映射层；不要在某个文案出口单独“解释过去”。故意不同的能力必须在契约测试和文档中写明原因。

## 4. 读取契约：从摘要到证据

### 4.1 分层

所有可能增长的读取接口按四层设计：

1. **摘要**：目标、状态计数、最近活动和继续入口；体量小，适合首次接入。
2. **有界列表**：明确 `limit`、排序、筛选和范围，返回是否截断及继续读取方式。
3. **单条详情**：按 id 读取一条事项、项目、评论或提议，必要时再带子资源。
4. **历史与证据**：按需读取评论线程、流转、修订或审计记录，不隐式塞进摘要。

`project get` 不应因为项目事项变多而无界膨胀；`project search` 不应把数百 KB 的全文命中一次性推给调用方。

### 4.2 有界结果元数据

列表、搜索和摘要接口必须明确以下信息（具体字段名以现有兼容出口为准）：

```json
{
  "matched": 181,
  "returned": 20,
  "truncated": true,
  "next": { "cursor": "..." }
}
```

调用方永远不能通过“输出看起来结束了”推断没有更多结果。没有继续读取能力的接口只能提供有意限制的摘要，不得暗示它是全量结果。

### 4.3 默认范围

- 日常工作列表默认聚焦未完成事项；
- 接手和历史检索要能明确选择所有状态，包括完成、挂起和废弃；
- `limit`、分页或游标必须在服务端生效，不能先取固定上限再由前端假分页；
- CLI 与 MCP 的默认限制可以不同，但必须在 schema 和说明中明确，不得静默不同。

## 5. 状态与来源契约

以下状态不能用一个布尔值或一条模糊文案混合表达：

- **empty**：没有填写或没有记录；
- **default_unconfirmed**：系统提供了默认内容，但主用户尚未确认；
- **confirmed**：主用户明确确认的内容；
- **pending_proposal**：Agent 已提交提议，等待审批；
- **approved**：审批已通过，但不代表动作已成功执行；
- **executed_success**：动作已执行并有成功证据；
- **executed_failure**：动作执行失败，并保留原因和处理建议；
- **result_unknown**：历史记录不足，不能推断结果。

读取档案、协议、审批记录和操作回执时，应同时给出来源范围（全局/项目）、作者或决定人、时间、修订/基准信息。空正文绝不能仅因有一行数据库记录就被标记为用户确认。

## 6. 写入与审批契约

每个写入口必须在 schema、Guide 和运行时结果中说清：

1. 是直接写入还是提交提议；
2. 是否需要主用户审批；
3. 审批后是立即执行、等待调用方继续，还是仅改变资料；
4. 使用哪个身份落账；
5. 如何用基准版本或修订号防止覆盖新内容；
6. 如何查询最终结果。

建议语义：

- `profile propose`、`protocol propose`：只创建待审批提议，审批前正式内容不变；
- 项目接手说明的 Agent 修改：通过 `project handoff-propose` 提交提议，审批页采纳后才写入正式说明；保留提议时原文、基准修订号和最终采纳正文。`project handoff-update` 仅供主用户直接保存；采纳时若基准修订已变化，必须拒绝并要求重新提交；
- 删除、配置和其他破坏性操作：遵守代码硬关口，不得由协议文本或 Skill 绕过；
- 任何批准结果都要区分“批准决定”和“执行结果”，失败不得伪装成成功。

提议应保存提交时的原内容/基准版本、提议正文、决定信息和最终采纳内容。基准已变化时必须拒绝静默覆盖，要求重新核对。

## 7. MCP 契约

- 工具名必须能在 `tools/list` 找到，并与 CLI/schema 的能力一一对应；
- 所有需要身份的写工具必须显式声明并转发 `actor` 等调用上下文；
- 未知入参必须显式拒绝，不能依赖 SDK 静默丢弃；
- `initialize.instructions` 只给稳定的接入路径和关键边界，不复制完整命令手册；
- `content[0].text` 若声明为 JSON，必须是可直接解析的 JSON；提醒、截断和继续读取信息应放在结构化字段中；
- 返回数组或对象可以因语义不同而不同，但 schema、文档和测试必须明确形状；
- MCP 不能提供 CLI 没有真实实现的“幻觉工具”，也不能让手工工具覆盖生成工具后丢失参数或风险信息。

## 8. 失败时的最小可继续信息

每个失败响应至少说明：

- 失败类别和稳定错误码；
- 本次请求是否产生了部分副作用；
- 是否需要用户审批、补充参数、重新读取还是联系其他角色；
- 如果存在继续入口，给出具体命令、工具或记录 id；
- 不把权限不足、未确认、执行失败和历史未知混成同一句“操作失败”。

Agent 应先读失败响应再重试。对删除、批准、重放等不可逆动作，不提供无条件自动重试。

## 9. 验收标准

一次 Agent 使用契约批次只有同时满足以下条件才算完成：

- 黄金路径中的每一步都有真实 CLI/MCP 出口或明确说明为何只支持 GUI；
- Skill、MCP instructions、CLI schema 和 GUI 入口互相不教错；
- 大结果有服务端边界、截断标记和继续读取方式；
- 空、默认未确认、已确认、提议、批准、执行结果和未知状态可区分；
- 代理写入的身份、审批和并发基准可追溯；
- 定向测试覆盖工具名、参数、actor 转发、未知参数拒绝、返回形状和失败语义；
- 未通过上述验证前，不升版本、不打包、不把修复标记为发布。

## 10. 变更规则

新增 Agent 能力时，先在本契约中说明它位于黄金路径的哪一步，再实现共享命令定义、CLI/MCP 映射、GUI 入口和 Skill 文案。发现单个出口问题时，优先查共享契约是否缺失，不以局部文案或单个测试补丁掩盖跨出口不一致。
